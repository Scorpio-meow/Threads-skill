# Benchmark 概要

[繁體中文](BENCHMARK.md) | [English](BENCHMARK.en.md) | **日本語** | [한국어](BENCHMARK.ko.md)

threads-api スキルの「スキルあり vs スキルなし」を 5 ラウンドにわたって評価した結果の概要です。問題とチェック項目は [`evals.json`](evals.json) に、各実行の項目ごとの判定と採点者が添えた根拠は [`benchmark.json`](benchmark.json) にあります。

## 平均所要時間とトークン使用量

| ラウンド | スキルあり | スキルなし |
|---|---|---|
| ラウンド 1 | 930 秒、20.5 万トークン | 840 秒、17.7 万トークン |
| ラウンド 2 | 599 秒、16.4 万トークン | 776 秒、16.5 万トークン |
| ラウンド 3 | 706 秒、17.8 万トークン | 963 秒、18.9 万トークン |
| ラウンド 4 | 964 秒、19.3 万トークン | 1,367 秒、18.4 万トークン |
| ラウンド 5 | 226 秒、12.1 万トークン | 282 秒、10.4 万トークン |

ラウンド 1 でスキルありのほうが遅く、使用量も多かったのは、スキル本体の読み込みに約 1.1 万トークンかかるためです。ラウンド 2・3 ではむしろスキルありのほうが速く、採点者は試行錯誤が減ったためと見ています。問題ごとの所要時間のばらつきは大きい（ラウンド 3 のスキルなしで 298〜1,613 秒）ため、これらの平均値は参考程度にとどめてください。ラウンド 4 は 1 問だけでしたが、ここでもスキルありのほうが速く終わりました。ラウンド 5 は所要時間も使用量もこれまでのラウンドを大きく下回っており、ほかのラウンドとそのまま比べるのは適切ではありません。スキルありは約 1.7 万トークン多く使いましたが、平均で 57 秒速く終わりました。

## 失点した項目

### スキルなし

| 問題 | 失点したラウンド | 失点の原因 |
|---|---|---|
| 2 | ラウンド 1、2 | ページングで `paging.next` だけをたどり、`paging.cursors.after` を読んでいませんでした。ドキュメントには投稿一覧のレスポンスに `next` は含まれないと明記されており、ドキュメントどおりなら最初のページしか取得できません。 |
| 2 | ラウンド 1、2 | トークンの延長時に、ドキュメントのルールどおりのチェックをしていませんでした。取り込んだトークンが発行から 24 時間以上経過していて、まだ期限切れでないことを確認していません。 |
| 3 | 3 ラウンドすべて | ゴースト投稿にアンケートを付けられないとはっきり言わず、「できないかもしれない」と述べるにとどまり、両方の機能を付けたまま送ってみる選択肢まで提示しました。ドキュメントには、ゴースト投稿で唯一使える追加機能はテキストのネタバレ防止だと明記されています。 |
| 3 | 3 ラウンドすべて | 実際に送信するパラメータ（`media_type`、`poll_attachment`、`is_ghost_post`）を回答に示さず、スクリプトの中にしか書いていませんでした。そのため、ユーザーは確認する前にそれを見ることができません。 |
| 3 | ラウンド 1、2 | `GET /me` は呼び出したものの、トークンの検証に使っただけで、どのアカウントに投稿するのかを先にユーザーに伝えて確認を待つことはしませんでした。ラウンド 2 の投稿スクリプトは、公開の前に `GET /me` を一度も呼び出しませんでした。 |
| 4 | ラウンド 2、3 | `profile_lookup` のフォロワー数の条件を古い 1,000 人のまま説明するか、まったく触れませんでした。2025 年 11 月から 100 人に引き下げられています。 |
| 5 | ラウンド 2、3 | まずネストされたリプライそのものに `manage_reply` を呼び出し、失敗してから上位のリプライを処理しました。ドキュメントには、ネストされたリプライは単独では非表示にできないと明記されています。 |
| 6 | ラウンド 4 | embed.js は読み込み時に一度しかページを走査しないと思い込み、投稿を 1 件ずつ別の iframe ページに入れていました。実際には embed.js を一度読み込み、投稿を挿入したあとに `window.instgrm.Embeds.process()` を呼べば済みます。 |
| 6 | ラウンド 4 | 「最初の数件だけ表示されて残りが止まる」原因を読み込みのタイミングだと考え、一度に多くの埋め込みを読み込んだことによるレート制限だとは気づきませんでした。 |
| 6 | ラウンド 4 | iframe の load イベントを成功とみなしていたため、レート制限を受けた埋め込みや壊れた埋め込みが代替カードに切り替わらず、失敗が続いても一時停止しませんでした。 |
| 6 | ラウンド 4 | 削除済みの投稿を正確に調べるには Meta アプリとトークンが必要だと考え、threads.com のページをスクレイピングしていました。oEmbed は 2026 年 3 月からトークン不要で、存在しない投稿には `code 24` を返します。 |
| 8 | ラウンド 5 | 権限の認可が 90 日間しか続かないことや、非公開アカウントは 90 日ごとに再認可が必要なことにまったく触れず、`data_access_expires_at` を追跡するよう勧めることもしませんでした。それどころか、定期的に延長していればユーザーはずっとログインしたままでいられるかのような回答でした。 |
| 9 | ラウンド 5 | `reply_control` を小文字に直したものの、大文字は読み取り時に `reply_audience` が返す形式にすぎないことを説明していませんでした。 |
| 9 | ラウンド 5 | エラー処理で `fbtrace_id` を示していませんでした。さらに、すべてのリクエストでトークンを URL のクエリパラメータに入れており、レスポンスが JSON でないときに呼ぶ `raise_for_status()` の例外メッセージには URL 全体が含まれるため、トークンが例外やログに漏れるおそれがあります。 |
| 10 | ラウンド 5 | 回答では 2 件の内容を要約しただけで、全文は別ファイルに置き、送信するパラメータも示していませんでした。ユーザーに明確な確認を求めず、そのまま投稿の実行を始めるよう案内していました。 |

採点者の結論は、これらの失点はほぼすべて、コードが書けないからではなく、ドキュメントのルールを知らないことが原因だというものでした。問題 2 のスキルなし版はラウンド 3 で満点を取っており、各問題 1 回しか実行しない場合、1 回の運の良し悪しで平均値が大きく変わることがわかります。ラウンド 5 の失点は、すべてがドキュメントの知識によるものではありません。問題 10 は投稿前に回答の中で全文を示してユーザーの確認を待たなかったこと、問題 9 の一部はトークンが漏れうるエラー処理によるものです。

### スキルあり

スキルありの回答は、どのラウンドでも失点した項目がありません。

### 減点はないが採点者が指摘した問題

- **ラウンド 1**：スキルあり版は、投稿後に投稿の URL を取得する際、ついでに `reply_audience` フィールドも要求していました。このフィールドには `threads_read_replies` 権限が必要で、権限がないと、成功した投稿が失敗したように見えてしまいます。スキルは、投稿後には `permalink` だけを取得するように修正しました。
- **ラウンド 2**：採点者はスキルありの回答をたどって、スキル自体に不正確な記述が 3 か所あることを突き止めました。`keyword_search` に cursor でのページングを勧めていた（ドキュメントには cursor パラメータが載っていない）、非公開アカウントの 90 日間の認可についてドキュメント同士が矛盾していると説明していた（実際にはドキュメントは一貫して延長できないと明記している）、「フォロワー関連の指標は別々に呼び出す」をドキュメントの規定として書いていた（実際には安全策にすぎない）、の 3 点です。
- **ラウンド 3**：採点者は言い過ぎている箇所をいくつか指摘し、いずれもスキルの言い回しに原因がありました。ゴースト投稿ではリンクプレビューを使えないとドキュメントに明記されていると説明していた（ドキュメントには、唯一使えるのはテキストのネタバレ防止だとしか書かれていない）、API が「必ず拒否する」と述べていた（API がどう反応するかはドキュメントに書かれていない）、`profile_lookup` と `profile_posts` のそれぞれ 1,000 回の上限を共通の枠として扱っていた（共通かどうかはドキュメントに書かれていない）、の 3 点です。現在の SKILL.md では、この 3 点はいずれも、ドキュメントに明確な記載がないことをそのまま説明するように改めています。
- **ラウンド 4**：採点者は、確認すべき観点を 2 つ追加するよう提案しました。保存しておいた埋め込みコードを innerHTML でそのまま挿入すると XSS の危険があること、そして古い threads.net のリンクからは threads.net ドメインの iframe が作られることです。スキルは、検証済みの URL から DOM メソッドで埋め込み用のマークアップを組み立てるよう改め、threads.net のリンクを threads.com に書き換えるか、CSP で両方のドメインを許可するよう案内するようにしました。また採点者は、チェック項目 8（投稿ページそのものを iframe に入れない）は embed.js を使う回答ならほぼ必ず通るため、両設定の差がほとんど出ないと指摘しています。
- **ラウンド 5**：問題 10 のチェック項目 1–5 と 7（絵文字の文字数の数え方、原文どおりの分割、`reply_to_id` でのつなぎ方、API に予約投稿の機能がないこと、トークンの確認、アカウントの確認）は両設定とも合格しており、差がほとんど出ません。差がついたのは項目 6、つまり回答の中に全文を示してユーザーに確認を求めることでした。問題 7 では、どちらの設定もリクエストの中で生のイベントを同期的に書き込み、Graph API での照会だけをバックグラウンドに回しています。スキルなし版の問題 9 はトークンを URL に入れており、`raise_for_status()` によって例外メッセージにトークンが出てしまうおそれがあります。この点はすでに失点に数えています（上の表を参照）。

## 制限

- 各問題・各設定とも 1 回しか実行していないため、ばらつきを推定できず、数字は傾向を見る程度にとどめてください。
- 評価は Claude でのみ行っており、Agent Skills に対応したほかのツールでは実際に検証していません。
- ラウンド 1–4 の API 呼び出しはすべて採点者が用意したモックサーバーに向けたものです。ラウンド 5 ではモックサーバーを使わず、回答側がローカルのモックや FastAPI の TestClient で自分のコードを確認し、採点者はコードを読んで判定しました。どのラウンドでも、実際の Threads アカウントには投稿していません。
- ドキュメントに書かれていない embed.js の挙動と oEmbed のエラーコードは、2026-10-14 に実際の embed.js を読み、oEmbed を実際に呼び出して確認したうえで、採点者に参考情報として渡しました。Meta が今後変更する可能性があります。
- 元の評価レポート（各実行の回答全文とコードを含む）はリポジトリに含めておらず、ここには採点データだけを残しています。
