# Benchmark 요약

[繁體中文](BENCHMARK.md) | [English](BENCHMARK.en.md) | [日本語](BENCHMARK.ja.md) | **한국어**

threads-api 스킬의 "스킬 있음 vs 스킬 없음" 5라운드 평가 요약입니다. 문제와 체크 항목은 [`evals.json`](evals.json)에, 실행별 항목 판정과 채점자가 첨부한 근거는 [`benchmark.json`](benchmark.json)에 있습니다.

## 평가 설정

| 항목 | 내용 |
|---|---|
| 답변 모델 | `claude-opus-5-5`(스킬 있음, 스킬 없음 두 설정 모두 같은 모델 사용) |
| 채점·분석 모델 | `claude-opus-5-5`, 채점자는 답변에 참여하지 않음 |
| 문제별·설정별 실행 횟수 | 1회 |
| 판정 방식 | 미리 정해 둔 체크 항목에 따라 하나씩 통과/불통과를 판정하고 근거(답변 원문, 코드 줄 번호, 모의 서버 실측 결과)를 첨부 |

|---|---|---|

| 2라운드 | 2026-10-13 08:14 | 2, 3, 4, 5 |

라운드 사이마다 채점 의견을 반영해 스킬을 수정했습니다. 1번 문제는 양쪽 모두 만점이라 차이를 가릴 수 없어서 2라운드부터는 2–5번 문제를 사용했고, 3번 문제는 2라운드부터 체크 항목이 하나 늘었습니다. 4라운드에서는 스킬에 11절(게시물 임베드)을 추가한 뒤 6번 문제를 새로 만들어 이 문제만 실행했습니다. 5라운드에서는 7–10번 문제(Webhooks, OAuth 로그인, 코드 리뷰, 스레드 대리 게시)를 새로 만들어 이 네 문제만 실행했습니다. 이 라운드에서는 스킬 없음 설정도 웹에서 공식 문서를 검색할 수 있었고 실제로 Webhooks와 OAuth 페이지를 찾아봤기 때문에, 두 설정의 차이가 이전 라운드보다 작습니다.

## 감점 항목

### 스킬 없음

| 문제 | 감점된 라운드 | 감점 원인 |
|---|---|---|
| 2 | 1, 2라운드 | 페이지네이션에서 `paging.next`만 따라가고 `paging.cursors.after`는 읽지 않았습니다. 문서에는 게시물 목록 응답에 `next`가 없다고 명시되어 있어, 문서대로라면 첫 페이지만 가져오게 됩니다. |
| 2 | 1, 2라운드 | 토큰 갱신 시 문서 규칙대로 확인하지 않았습니다. 가져온 토큰이 발급된 지 24시간이 지났는지, 아직 만료되지 않았는지 확인하지 않았습니다. |
| 3 | 세 라운드 모두 | 고스트 게시물에 투표를 붙일 수 없다고 명확히 말하지 않고 "안 될 수도 있다"고만 했으며, 두 기능을 함께 보내 보자는 선택지까지 제시했습니다. 문서에는 고스트 게시물이 지원하는 유일한 부가 기능이 텍스트 스포일러라고 명시되어 있습니다. |
| 3 | 세 라운드 모두 | 실제로 보낼 파라미터(`media_type`, `poll_attachment`, `is_ghost_post`)를 답변에 적지 않고 스크립트 안에만 넣어, 사용자가 확인하기 전에 볼 수 없었습니다. |
| 3 | 1, 2라운드 | `GET /me`를 호출했지만 토큰 검증에만 쓰고, 어느 계정으로 게시할지 먼저 알린 뒤 확인을 기다리지 않았습니다. 2라운드의 게시 스크립트는 게시 전에 `GET /me`를 아예 호출하지 않았습니다. |
| 4 | 2, 3라운드 | `profile_lookup`의 팔로워 기준을 예전 값인 1,000이라고 하거나 아예 언급하지 않았습니다. 2025년 11월부터 100으로 낮아졌습니다. |
| 5 | 2, 3라운드 | 중첩 답글 자체에 `manage_reply`를 먼저 호출하고, 실패한 뒤에야 상위 답글을 처리했습니다. 문서에는 중첩 답글을 단독으로 숨길 수 없다고 명시되어 있습니다. |
| 6 | 4라운드 | embed.js가 로드될 때 페이지를 한 번만 훑는다고 생각해 게시물마다 별도의 iframe 페이지로 감쌌습니다. 실제로는 embed.js를 한 번만 로드하고, 게시물을 넣은 뒤 `window.instgrm.Embeds.process()`를 호출하면 됩니다. |
| 6 | 4라운드 | "처음 몇 개만 나오고 나머지는 멈춘다"는 증상을 로딩 타이밍 문제로 보고, 한꺼번에 너무 많은 임베드를 불러와 레이트 리밋에 걸렸다는 점은 놓쳤습니다. |
| 6 | 4라운드 | iframe의 load 이벤트를 성공으로 간주해, 레이트 리밋에 걸리거나 깨진 임베드가 대체 카드로 바뀌지 않았고 실패가 이어져도 잠시 멈추지 않았습니다. |
| 6 | 4라운드 | 삭제된 게시물을 정확히 확인하려면 Meta 앱과 토큰이 필요하다고 보고 threads.com 페이지를 스크레이핑했습니다. oEmbed는 2026년 3월부터 토큰 없이 쓸 수 있고, 없는 게시물에는 `code 24`를 반환합니다. |
| 8 | 5라운드 | 권한 승인이 90일만 유지된다는 점, 비공개 계정은 90일마다 다시 승인해야 한다는 점을 전혀 언급하지 않았고 `data_access_expires_at`을 추적하라는 제안도 없었습니다. 오히려 주기적으로 갱신하기만 하면 사용자가 계속 로그인 상태를 유지할 수 있는 것처럼 답했습니다. |
| 9 | 5라운드 | `reply_control`을 소문자로 고쳤지만, 대문자는 읽을 때 `reply_audience`가 반환하는 형식일 뿐이라는 점은 설명하지 않았습니다. |
| 9 | 5라운드 | 오류 처리에서 `fbtrace_id`를 보여 주지 않았습니다. 게다가 모든 요청에서 토큰을 URL 쿼리 파라미터에 넣었고, 응답이 JSON이 아닐 때 호출하는 `raise_for_status()`의 예외 메시지에는 전체 URL이 들어가므로 토큰이 예외와 로그로 새어 나갈 수 있습니다. |
| 10 | 5라운드 | 답변에서 두 게시물의 내용을 요약만 하고 전체 텍스트는 별도 파일에 두었으며, 보낼 파라미터도 나열하지 않았습니다. 사용자에게 명확한 확인을 받지 않고 바로 게시 실행을 시작하라고 안내했습니다. |

채점자의 결론은 이 감점이 거의 모두 코드를 못 짜서가 아니라 문서에 있는 규칙을 몰라서 생겼다는 것입니다. 2번 문제의 스킬 없는 버전이 3라운드에서 만점을 받은 것을 보면, 문제마다 한 번씩만 실행할 때는 한 번의 운이 평균값을 크게 흔들 수 있습니다. 5라운드의 감점은 모두 문서 지식 때문만은 아닙니다. 10번 문제는 게시 전에 답변에서 전체 내용을 보여 주고 사용자 확인을 기다리지 않은 것이고, 9번 문제의 일부는 토큰이 새어 나갈 수 있는 오류 처리 때문입니다.

### 스킬 있음

스킬 있음 답변은 어느 라운드에서도 감점된 항목이 없습니다.

### 감점은 없었지만 채점자가 지적한 문제

- **1라운드**: 스킬 있음 버전이 게시 후 게시물 URL을 조회하면서 `reply_audience` 필드까지 함께 요청했습니다. 이 필드는 `threads_read_replies` 권한이 필요해서, 권한이 없으면 성공한 게시가 실패한 것처럼 보일 수 있습니다. 게시 후에는 `permalink`만 조회하도록 스킬을 수정했습니다.
- **2라운드**: 채점자가 스킬 있음 버전의 답변을 통해 스킬 자체의 부정확한 표현 세 군데를 찾아냈습니다. `keyword_search`에 cursor 페이지네이션을 권장한 것(문서에는 cursor 파라미터가 없음), 비공개 계정의 90일 승인을 문서끼리 모순된다고 한 것(실제로는 문서가 일관되게 연장 불가라고 명시), "팔로워 관련 지표는 따로 호출"을 문서 규정처럼 쓴 것(실제로는 보수적인 방식일 뿐)입니다.
- **3라운드**: 채점자가 지나치게 단정한 표현 몇 군데를 지적했고, 이 역시 모두 스킬의 문구에서 비롯된 것이었습니다. 고스트 게시물에 링크 미리보기를 쓸 수 없다고 문서에 명시되어 있다고 한 것(문서는 텍스트 스포일러만 지원한다고만 함), API가 "반드시 거부한다"고 한 것(문서에는 API가 어떻게 반응하는지 나와 있지 않음), `profile_lookup`과 `profile_posts`의 각 1,000회 한도를 공유 한도로 취급한 것(문서에 공유 여부가 나와 있지 않음)입니다. 현재 SKILL.md는 이 세 가지 모두 문서가 불분명하다고 사실대로 설명하도록 수정되어 있습니다.
- **4라운드**: 채점자는 확인할 관점 두 가지를 더 제안했습니다. 저장해 둔 임베드 코드를 innerHTML로 그대로 넣으면 XSS 위험이 있다는 점, 그리고 예전 threads.net 링크는 threads.net 도메인의 iframe을 만든다는 점입니다. 스킬은 검증된 URL로 DOM 메서드를 써서 임베드 마크업을 만들도록 바꿨고, threads.net 링크를 threads.com으로 바꾸거나 CSP에서 두 도메인을 모두 허용하라고 안내합니다. 채점자는 또 8번 체크 항목(게시물 페이지 자체를 iframe에 넣지 않기)은 embed.js를 쓰는 답변이면 거의 다 통과해 두 설정의 차이를 가리지 못한다고 지적했습니다.
- **5라운드**: 10번 문제의 1–5번, 7번 체크 항목(이모지 글자 수 계산 방식, 원문 그대로 나누기, `reply_to_id`로 이어 붙이기, API에 예약 게시 기능이 없다는 점, 토큰 확인, 계정 확인)은 두 설정 모두 통과해 차이를 거의 가리지 못했습니다. 차이를 만든 것은 6번 항목, 즉 답변에 전체 내용을 보여 주고 사용자에게 확인을 받는 것이었습니다. 7번 문제에서는 두 설정 모두 요청 안에서 원본 이벤트를 동기적으로 저장하고, Graph API 조회만 백그라운드로 넘겼습니다. 스킬 없음 버전의 9번 문제는 토큰을 URL에 넣어서 `raise_for_status()`가 예외 메시지에 토큰을 노출할 수 있습니다. 이 점은 이미 감점에 반영했습니다(위 표 참고).

## 제한 사항

- 문제마다 설정별로 한 번씩만 실행했기 때문에 편차를 추정할 수 없으며, 수치는 경향 정도로만 봐 주세요.
- Claude에서만 평가했고, Agent Skills를 지원하는 다른 도구에서는 실제로 테스트하지 않았습니다.
- 1–4라운드의 API 호출은 모두 채점자가 띄운 모의 서버로 보냈습니다. 5라운드에는 모의 서버가 없었고, 답변 쪽이 로컬 모의 객체나 FastAPI의 TestClient로 자기 코드를 확인했으며 채점자는 코드를 읽고 판정했습니다. 어느 라운드에서도 실제 Threads 계정으로 게시하지는 않았습니다.
- 문서에 없는 embed.js 동작과 oEmbed 오류 코드는 2026-10-14에 실제 embed.js를 읽고 oEmbed를 직접 호출해 확인한 뒤 채점자에게 참고 자료로 제공했습니다. Meta가 앞으로 바꿀 수 있습니다.
- 원본 평가 보고서(실행별 전체 답변과 코드 포함)는 repo에 넣지 않았고, 여기에는 채점 데이터만 남겼습니다.
