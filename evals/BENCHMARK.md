# Benchmark 摘要

threads-api 技能「有技能 vs 沒技能」五輪評測的摘要。題目和檢查項目在 [`evals.json`](evals.json)，每次執行的逐條判定與評分者附上的證據在 [`benchmark.json`](benchmark.json)。

## 平均耗時與 token 用量

| 輪次 | 有技能 | 沒技能 |
|---|---|---|
| 第 1 輪 | 930 秒、20.5 萬 token | 840 秒、17.7 萬 token |
| 第 2 輪 | 599 秒、16.4 萬 token | 776 秒、16.5 萬 token |
| 第 3 輪 | 706 秒、17.8 萬 token | 963 秒、18.9 萬 token |
| 第 4 輪 | 964 秒、19.3 萬 token | 1,367 秒、18.4 萬 token |
| 第 5 輪 | 226 秒、12.1 萬 token | 282 秒、10.4 萬 token |

第 1 輪有技能比較慢、用量也比較多，因為技能本身要讀進約 1.1 萬 token；第 2、3 輪反而比較快，評分者認為是少了試錯。各題耗時差異很大（第 3 輪沒技能介於 298 到 1,613 秒），這些平均值只供參考。第 4 輪只跑一題，有技能一樣比較快。第 5 輪的耗時和用量都遠低於前幾輪，不宜和其他輪直接比較；有技能多用了約 1.7 萬 token，但平均快 57 秒。

## 失分項目

### 沒技能

| 題目 | 失分的輪次 | 失分原因 |
|---|---|---|
| 2 | 第 1、2 輪 | 翻頁只跟著 `paging.next` 走，沒讀 `paging.cursors.after`；文件寫明貼文列表的回應沒有 `next`，照文件的說法只會抓到第一頁。 |
| 2 | 第 1、2 輪 | token 續期沒照文件規則檢查：匯入的 token 沒確認已發出滿 24 小時、還沒過期。 |
| 3 | 三輪都有 | 沒有明確說限時貼文不能附投票，只說「可能不行」，還提供把兩個功能一起送出去試試看的選項。文件寫明限時貼文唯一支援的附加功能是文字防雷。 |
| 3 | 三輪都有 | 回覆裡沒列出實際要送出的參數（`media_type`、`poll_attachment`、`is_ghost_post`），只放在腳本裡，使用者確認前看不到。 |
| 3 | 第 1、2 輪 | 有呼叫 `GET /me`，但只拿來驗證 token，沒有先告訴使用者要發到哪個帳號、等確認再發；第 2 輪的發文腳本則在發布前完全沒有呼叫 `GET /me`。 |
| 4 | 第 2、3 輪 | `profile_lookup` 的粉絲門檻說成舊的 1,000，或完全沒提；2025 年 11 月起已降到 100。 |
| 5 | 第 2、3 輪 | 先對巢狀回覆本身呼叫 `manage_reply`，失敗才改處理上層留言；文件寫明巢狀回覆不能單獨隱藏。 |
| 6 | 第 4 輪 | 以為 embed.js 只會在載入時掃描一次頁面，於是把每則貼文各包進一個 iframe 頁面；其實載入一次 embed.js、插入貼文後呼叫 `window.instgrm.Embeds.process()` 就行。 |
| 6 | 第 4 輪 | 把「前幾則會出來、後面卡住」歸因於載入時機，沒想到是一次載入太多嵌入而被限流。 |
| 6 | 第 4 輪 | 以 iframe 的 load 事件當成載入成功，被限流或失效的嵌入永遠不會換成備援卡片，連續失敗也不會暫停。 |
| 6 | 第 4 輪 | 以為要準確檢查貼文是否被刪需要 Meta App 和 token，改去爬 threads.com 頁面；其實 oEmbed 從 2026 年 3 月起不需要 token，貼文不存在時會回 `code 24`。 |
| 8 | 第 5 輪 | 完全沒提到權限授權只有 90 天、私人帳號每 90 天必須重新授權，也沒建議追蹤 `data_access_expires_at`；回覆反而暗示只要定期續期，使用者就能一直保持登入。 |
| 9 | 第 5 輪 | 把 `reply_control` 改成小寫，但沒說明大寫只是讀取時 `reply_audience` 回傳的格式。 |
| 9 | 第 5 輪 | 錯誤處理沒帶出 `fbtrace_id`；而且每個請求都把 token 放在網址的查詢參數裡，回應不是 JSON 時呼叫的 `raise_for_status()` 產生的例外訊息含完整網址，可能把 token 洩漏到例外和 log。 |
| 10 | 第 5 輪 | 回覆只摘要兩則的內容，完整文字放在另一個檔案，也沒列出要送出的參數；沒有請使用者明確確認，而是直接告訴使用者怎麼開始執行發文。 |

評分者的結論是：這些失分幾乎都是不知道文件裡的規則，而不是程式寫不出來。第 2 題沒技能的版本在第 3 輪拿到滿分，可見每題只跑一次時，一次運氣好壞就會讓平均值大幅變動。第 5 輪的失分則不全是文件知識：第 10 題是代發前沒在回覆裡列出完整內容並等使用者確認，第 9 題有一部分是錯誤處理可能洩漏 token。

### 有技能

有技能的版本在各輪都沒有失分項目。

### 沒有扣分但評分者指出的問題

- **第 1 輪**：有技能的版本在發文後查詢貼文網址時，順便要了 `reply_audience` 欄位；這個欄位需要 `threads_read_replies` 權限，沒有權限時會讓成功的發文看起來像失敗。技能改為發文後只查 `permalink`。
- **第 2 輪**：評分者從有技能的回覆裡，追查到技能本身三處不精確的寫法：對 `keyword_search` 建議用 cursor 翻頁（文件沒列 cursor 參數）、把私人帳號 90 天授權說成文件互相矛盾（其實文件一致寫明不能延長）、把「粉絲相關指標分開呼叫」寫成文件規定（其實只是保守做法）。
- **第 3 輪**：評分者指出幾處說得太滿的地方，也都追溯到技能的措辭：把限時貼文不能有連結預覽說成文件寫明（文件只說唯一支援文字防雷）、說 API「一定會拒絕」（文件沒寫 API 會怎麼反應）、把 `profile_lookup` 和 `profile_posts` 各自 1,000 次的上限當成共用額度（文件沒說是否共用）。目前的 SKILL.md 對這三點都已改成照實說明文件沒寫清楚。
- **第 4 輪**：評分者建議再加兩個檢查角度：直接用 innerHTML 塞入存下來的嵌入碼有 XSS 風險，以及舊的 threads.net 連結會產生 threads.net 網域的 iframe。技能已改為從驗證過的網址用 DOM 方法組出嵌入標記，並提醒把 threads.net 連結改成 threads.com，或在 CSP 同時允許兩個網域。評分者也指出第 8 個檢查項目（不要把貼文頁本身放進 iframe）幾乎任何用 embed.js 的答案都會通過，鑑別力不足。
- **第 5 輪**：第 10 題的第 1–5、7 個檢查項目（emoji 的字數算法、照原文拆段、用 `reply_to_id` 串起來、API 沒有排程功能、檢查 token、確認帳號）兩種設定都通過，鑑別力不足，真正分出差別的是第 6 項：在回覆裡列出完整內容並請使用者確認。第 7 題兩邊都在請求裡同步寫入原始事件，只把查詢 Graph API 的部分放到背景執行。沒技能的第 9 題把 token 放在網址裡，`raise_for_status()` 可能讓 token 出現在例外訊息裡；這一點已經算進失分（見上表）。

## 限制

- 每題每種設定只跑一次，無法估計變異，數字只能看方向。
- 只在 Claude 上評測，其他支援 Agent Skills 的工具沒有實測。
- 第 1–4 輪的 API 呼叫都打在評分者架的模擬伺服器上；第 5 輪沒有模擬伺服器，作答者用本機的模擬或 FastAPI 的 TestClient 自行檢查程式，評分者則閱讀程式碼判定。各輪都沒有對真實的 Threads 帳號發文。
- 官方文件沒寫到的 embed.js 行為和 oEmbed 錯誤碼，是 2026-10-14 實際讀取線上的 embed.js、實際呼叫 oEmbed 確認後提供給評分者參考的；Meta 之後可能改變。
- 原始評測報告（含每次執行的完整回覆與程式）沒有放進 repo，這裡只保留評分資料。
