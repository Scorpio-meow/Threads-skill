# Benchmark 요약

[繁體中文](BENCHMARK.md) | [English](BENCHMARK_en.md) | [日本語](BENCHMARK_ja.md) | **한국어**

threads-api 스킬의 "스킬 있음 vs 스킬 없음" 7라운드 평가 요약입니다. 문제와 체크 항목은 [`evals.json`](evals.json)에, 실행별 항목 판정과 채점자가 첨부한 근거는 [`benchmark.json`](benchmark.json)에 있습니다.

## 평가 설정

| 항목 | 내용 |
|---|---|
| 답변 모델 | `claude-opus-5-5`(스킬 있음, 스킬 없음 두 설정 모두 같은 모델 사용) |
| 채점·분석 모델 | `claude-opus-5-5`, 채점자는 답변에 참여하지 않음 |
| 문제별·설정별 실행 횟수 | 1회 |
| 판정 방식 | 미리 정해 둔 체크 항목에 따라 하나씩 통과/불통과를 판정하고 근거(답변 원문, 코드 줄 번호, 모의 서버 실측 결과)를 첨부 |

| 라운드 | 시각(UTC) | 문제 |
|---|---|---|
| 1라운드 | 2026-10-13 07:07 | 1, 2, 3 |
| 2라운드 | 2026-10-13 08:14 | 2, 3, 4, 5 |
| 3라운드 | 2026-10-14 02:13 | 2, 3, 4, 5 |
| 4라운드 | 2026-10-14 07:23 | 6 |
| 5라운드 | 2026-10-18 12:47 | 7, 8, 9, 10 |
| 6라운드 | 2026-10-18 16:34 | 2, 4, 7, 8 |
| 7라운드 | 2026-10-19 12:22 | 1–10 |

라운드 사이마다 채점 의견을 반영해 스킬을 수정했습니다. 1번 문제는 양쪽 모두 만점이라 차이를 가릴 수 없어서 2라운드부터는 2–5번 문제를 사용했고, 3번 문제는 2라운드부터 체크 항목이 하나 늘었습니다. 4라운드에서는 스킬에 11절(게시물 임베드)을 추가한 뒤 6번 문제를 새로 만들어 이 문제만 실행했습니다. 5라운드에서는 7–10번 문제(Webhooks, OAuth 로그인, 코드 리뷰, 스레드 대리 게시)를 새로 만들어 이 네 문제만 실행했습니다. 이 라운드에서는 스킬 없음 설정도 웹에서 공식 문서를 검색할 수 있었고 실제로 Webhooks와 OAuth 페이지를 찾아봤기 때문에, 두 설정의 차이가 이전 라운드보다 작습니다. 6라운드에서는 스킬 1.3 버전으로 2, 4, 7, 8번 문제를 다시 실행해, 아직 평가하지 않은 두 가지 변경을 검증했습니다. 10절의 webhook 중복 제거 규칙과, 8절에서 `debug_token`에 앱 토큰도 쓸 수 있다고 설명한 부분입니다. 이 라운드에서는 두 설정 모두 웹을 쓸 수 없었고 스킬 없음 설정은 모델 자체의 지식만으로 답했으므로, 7, 8번 문제는 5라운드와 그대로 비교하기 어렵습니다. 2번 문제의 스킬 없음과 8번 문제의 두 설정은 도중에 멈춘 뒤, 2026-10-19 11:26(UTC)에 같은 지시로 처음부터 다시 실행했습니다. 7라운드에서는 스킬 1.4 버전으로 10개 문제를 모두 다시 실행해, 14절의 Python 참조 클라이언트를 `scripts/threads_client.py`로 옮긴 뒤에도 퇴보가 없는지 확인했습니다. 스킬은 `threads-api` 폴더 전체(`scripts/` 포함)로 설치했고, 두 설정 모두 웹을 쓸 수 없었습니다. 4번 문제는 이 라운드부터 체크 항목이 7개이며, 새로 추가된 7번 항목은 `debug_token`에 앱 토큰을 쓸 수 있다는 점입니다. 페이지네이션은 6라운드부터의 판정 기준을 따라, 응답에 `paging.next`가 있을 때만 페이지를 넘기는 코드는 불통과로 판정했고, 이 라운드에서는 5, 9번 문제에도 같은 기준을 적용했습니다(2, 3라운드의 5번 문제에서는 이런 코드를 단서를 달아 통과시켰습니다). 이 라운드의 스킬 스냅숏은 14절에 '스킬 파일이 디스크에 없을 때 표준 입력으로 클라이언트를 실행한다'는 설명이 추가되기 약 1분 전에 만든 것이어서, 이 설명은 평가 범위에 들어가지 않습니다.

1라운드에서 스킬 있음 쪽이 더 느리고 사용량도 많았던 것은 스킬 자체를 읽는 데 약 1.1만 토큰이 들기 때문입니다. 2, 3라운드에서는 오히려 더 빨랐는데, 채점자는 시행착오가 줄었기 때문이라고 봤습니다. 문제별 소요 시간 차이가 매우 크므로(3라운드 스킬 없음 기준 298초에서 1,613초까지) 이 평균값은 참고용으로만 봐 주세요. 4라운드는 문제 하나만 실행했으며, 여기서도 스킬 있음 쪽이 더 빨랐습니다. 5라운드는 소요 시간과 사용량 모두 이전 라운드보다 훨씬 적어서 다른 라운드와 그대로 비교하기는 어렵습니다. 스킬 있음 쪽은 약 1.7만 토큰을 더 썼지만 평균 57초 더 빨랐습니다. 6라운드에서는 스킬 있음 쪽이 평균 117초 더 느렸고 약 4만 토큰을 더 썼습니다. 네 문제 중 4, 7번은 스킬 있음 쪽이 더 빨랐고, 평균이 느려진 것은 주로 2번 문제(스킬 있음 1,553초, 스킬 없음 811초) 때문입니다. 7라운드는 20개 답변을 동시에 실행했습니다. 스킬 있음 쪽이 평균 100초 더 빨랐고 약 1.4만 토큰을 더 썼으며, 10개 문제 중 8개에서 더 빨랐습니다. 가장 오래 걸린 것은 스킬 없음의 6번 문제(1,186초)입니다.

## 감점 항목

### 스킬 없음

| 문제 | 감점된 라운드 | 감점 원인 |
|---|---|---|
| 2 | 1, 2, 6, 7라운드 | 페이지네이션에서 `paging.next`만 따라가고 `paging.cursors.after`는 읽지 않았습니다(6라운드에서는 `paging.next`가 있을 때만 읽었습니다). 문서에는 게시물 목록 응답에 `next`가 없다고 명시되어 있어, 문서대로라면 첫 페이지만 가져오게 됩니다. |
| 2 | 1, 2라운드 | 토큰 갱신 시 문서 규칙대로 확인하지 않았습니다. 가져온 토큰이 발급된 지 24시간이 지났는지, 아직 만료되지 않았는지 확인하지 않았습니다. |
| 2 | 7라운드 | 게시물별 인사이트를 `/{media-id}/threads_insights`로 요청했습니다. 올바른 엔드포인트는 `/{media-id}/insights`입니다(`threads_insights`는 계정 단위 엔드포인트). 직접 만든 모의 서버도 같은 경로를 써서 테스트에서는 잡지 못했고, 채점자가 문서대로의 경로로 확인하자 모든 게시물의 수치가 비어 있었습니다. |
| 3 | 1–3라운드 | 고스트 게시물에 투표를 붙일 수 없다고 명확히 말하지 않고 "안 될 수도 있다"고만 했으며, 두 기능을 함께 보내 보자는 선택지까지 제시했습니다. 문서에는 고스트 게시물이 지원하는 유일한 부가 기능이 텍스트 스포일러라고 명시되어 있습니다. |
| 3 | 1–3, 7라운드 | 실제로 보낼 파라미터(`media_type`, `poll_attachment`, `is_ghost_post`)를 답변에 적지 않고 스크립트 안에만 넣어, 사용자가 확인하기 전에 볼 수 없었습니다. |
| 3 | 1, 2라운드 | `GET /me`를 호출했지만 토큰 검증에만 쓰고, 어느 계정으로 게시할지 먼저 알린 뒤 확인을 기다리지 않았습니다. 2라운드의 게시 스크립트는 게시 전에 `GET /me`를 아예 호출하지 않았습니다. |
| 4 | 2, 3, 6, 7라운드 | `profile_lookup`의 팔로워 기준을 예전 값인 1,000이라고 하거나 아예 언급하지 않았습니다. 2025년 11월부터 100으로 낮아졌습니다. |
| 4 | 7라운드 | scopes 확인에 `debug_token`을 권했지만, `access_token`에 앱 토큰을 쓸 수 있어 Threads 테스터가 필요 없다는 점도, `input_token`과 같은 앱의 것이어야 한다는 점도 설명하지 않았습니다. 첨부한 스크립트는 사용자 자신의 토큰으로 호출해서, 그 계정이 테스터가 아니면 확인할 수 없습니다. 7라운드에 추가한 7번 체크 항목입니다. |
| 5 | 2, 3라운드 | 중첩 답글 자체에 `manage_reply`를 먼저 호출하고, 실패한 뒤에야 상위 답글을 처리했습니다. 문서에는 중첩 답글을 단독으로 숨길 수 없다고 명시되어 있습니다. |
| 5 | 7라운드 | 응답에 `paging.next`가 있을 때만 페이지를 넘겨서, 문서대로의 형식인 응답에서는 첫 페이지만 읽습니다. 채점자 검증에서 두 번째 페이지의 키워드 답글은 숨겨지지 않았습니다. 2, 3라운드의 판정이라면 단서를 달아 통과했겠지만, 이 라운드는 6라운드부터의 기준을 썼습니다. |
| 6 | 4, 7라운드 | embed.js가 로드될 때 페이지를 한 번만 훑는다고 생각해 게시물마다 별도의 iframe 페이지로 감쌌습니다. 실제로는 embed.js를 한 번만 로드하고, 게시물을 넣은 뒤 `window.instgrm.Embeds.process()`를 호출하면 됩니다. |
| 6 | 4, 7라운드 | "처음 몇 개만 나오고 나머지는 멈춘다"는 증상을 로딩 타이밍 문제로 보고, 한꺼번에 너무 많은 임베드를 불러와 레이트 리밋에 걸렸다는 점은 놓쳤습니다. |
| 6 | 4, 7라운드 | iframe의 load 이벤트를 성공으로 간주해, 레이트 리밋에 걸리거나 깨진 임베드가 대체 카드로 바뀌지 않았고 실패가 이어져도 잠시 멈추지 않았습니다. |
| 6 | 4라운드 | 삭제된 게시물을 정확히 확인하려면 Meta 앱과 토큰이 필요하다고 보고 threads.com 페이지를 스크레이핑했습니다. oEmbed는 2026년 3월부터 토큰 없이 쓸 수 있고, 없는 게시물에는 `code 24`를 반환합니다. |
| 6 | 7라운드 | 주간 점검에 oEmbed를 쓰게 됐지만, 토큰이 필요한지 모르겠다고 하면서 60일짜리 사용자 토큰을 준비하라고까지 권했습니다. 삭제 조건도 반대로 되어 있어서 `code 100`(파라미터 오류)이면 게시물을 지우고, 게시물이 없다는 뜻인 `code 24`는 확인 필요로만 표시했습니다. 채점자 검증에서 삭제된 게시물은 끝내 목록에서 빠지지 않았습니다. |
| 7 | 6, 7라운드 | `target_id`를 항상 브랜드 계정의 user ID로 취급했습니다. `replies` 이벤트의 `target_id`는 실제로는 media ID라서, 채점자가 문서대로의 형식으로 답글 이벤트를 보내자 6라운드의 코드는 모두 ignored로 표시하고 버렸습니다. 7라운드의 코드는 이벤트를 버리지는 않았지만, 답글 이벤트마다 토큰의 계정을 확인하라는 경고를 남겼습니다. |
| 7 | 6, 7라운드 | 이벤트가 오지 않는 이유를 설명하면서 비즈니스 인증이 필요하다는 점을 언급하지 않았습니다. |
| 8 | 5, 6, 7라운드 | 권한 승인이 90일만 유지된다는 점, 비공개 계정은 90일마다 다시 승인해야 한다는 점을 전혀 언급하지 않았고 `data_access_expires_at`을 추적하라는 제안도 없었습니다. 오히려 주기적으로 갱신하기만 하면 사용자가 계속 로그인 상태를 유지할 수 있는 것처럼 답했습니다. |
| 9 | 5, 7라운드 | `reply_control`을 소문자로 고쳤지만, 대문자는 읽을 때 `reply_audience`가 반환하는 형식일 뿐이라는 점은 설명하지 않았습니다. |

| 10 | 7라운드 | 현재 환경에 `THREADS_ACCESS_TOKEN`이 있는지 확인하지 않았고, 여기서는 토큰을 읽을 수 없다는 점도 답변에서 알리지 않았습니다. 마지막에는 토큰이 필요한 사전 점검을 바로 실행해 주겠다고 제안했습니다. |

채점자의 결론은 이 감점이 거의 모두 코드를 못 짜서가 아니라 문서에 있는 규칙을 몰라서 생겼다는 것입니다. 2번 문제의 스킬 없는 버전이 3라운드에서 만점을 받은 것을 보면, 문제마다 한 번씩만 실행할 때는 한 번의 운이 평균값을 크게 흔들 수 있습니다. 5라운드의 감점은 모두 문서 지식 때문만은 아닙니다. 10번 문제는 게시 전에 답변에서 전체 내용을 보여 주고 사용자 확인을 기다리지 않은 것이고, 9번 문제의 일부는 토큰이 새어 나갈 수 있는 오류 처리 때문입니다. 6라운드 스킬 없음의 감점 다섯 개는 다시 모두 문서 지식에 관한 것이었습니다. 페이지네이션, 팔로워 기준, `target_id`의 의미, 비즈니스 인증, 90일 승인이며, 이 가운데 페이지네이션, 팔로워 기준, 90일 승인은 이전 라운드에서도 감점된 적이 있습니다. 7라운드 스킬 없음의 감점 18개 중 15개는 문서 지식에 관한 것이었습니다. 게시물별 인사이트 엔드포인트와 `debug_token`에 앱 토큰을 쓸 수 있다는 점 두 가지를 빼면, 페이지네이션, 팔로워 기준, 6번 문제의 임베드와 oEmbed, `target_id`, 비즈니스 인증, 90일 승인, `reply_audience`의 대문자 형식은 모두 이전 라운드에서도 감점된 적이 있습니다. 나머지 3개는 대리 작업 방식에 관한 것으로, 보낼 내용을 답변에 보여 주고 사용자 확인을 받지 않은 것(3, 10번 문제)과, 토큰을 확인하지 않고 여기서는 읽을 수 없다는 점도 알리지 않은 것(10번 문제)입니다.

### 감점은 없었지만 채점자가 지적한 문제

- **1라운드**: 스킬 있음 버전이 게시 후 게시물 URL을 조회하면서 `reply_audience` 필드까지 함께 요청했습니다. 이 필드는 `threads_read_replies` 권한이 필요해서, 권한이 없으면 성공한 게시가 실패한 것처럼 보일 수 있습니다. 게시 후에는 `permalink`만 조회하도록 스킬을 수정했습니다.
- **2라운드**: 채점자가 스킬 있음 버전의 답변을 통해 스킬 자체의 부정확한 표현 세 군데를 찾아냈습니다. `keyword_search`에 cursor 페이지네이션을 권장한 것(문서에는 cursor 파라미터가 없음), 비공개 계정의 90일 승인을 문서끼리 모순된다고 한 것(실제로는 문서가 일관되게 연장 불가라고 명시), "팔로워 관련 지표는 따로 호출"을 문서 규정처럼 쓴 것(실제로는 보수적인 방식일 뿐)입니다.
- **3라운드**: 채점자가 지나치게 단정한 표현 몇 군데를 지적했고, 이 역시 모두 스킬의 문구에서 비롯된 것이었습니다. 고스트 게시물에 링크 미리보기를 쓸 수 없다고 문서에 명시되어 있다고 한 것(문서는 텍스트 스포일러만 지원한다고만 함), API가 "반드시 거부한다"고 한 것(문서에는 API가 어떻게 반응하는지 나와 있지 않음), `profile_lookup`과 `profile_posts`의 각 1,000회 한도를 공유 한도로 취급한 것(문서에 공유 여부가 나와 있지 않음)입니다. 현재 SKILL.md는 이 세 가지 모두 문서가 불분명하다고 사실대로 설명하도록 수정되어 있습니다.
- **4라운드**: 채점자는 확인할 관점 두 가지를 더 제안했습니다. 저장해 둔 임베드 코드를 innerHTML로 그대로 넣으면 XSS 위험이 있다는 점, 그리고 예전 threads.net 링크는 threads.net 도메인의 iframe을 만든다는 점입니다. 스킬은 검증된 URL로 DOM 메서드를 써서 임베드 마크업을 만들도록 바꿨고, threads.net 링크를 threads.com으로 바꾸거나 CSP에서 두 도메인을 모두 허용하라고 안내합니다. 채점자는 또 8번 체크 항목(게시물 페이지 자체를 iframe에 넣지 않기)은 embed.js를 쓰는 답변이면 거의 다 통과해 두 설정의 차이를 가리지 못한다고 지적했습니다.
- **5라운드**: 10번 문제의 1–5번, 7번 체크 항목(이모지 글자 수 계산 방식, 원문 그대로 나누기, `reply_to_id`로 이어 붙이기, API에 예약 게시 기능이 없다는 점, 토큰 확인, 계정 확인)은 두 설정 모두 통과해 차이를 거의 가리지 못했습니다. 차이를 만든 것은 6번 항목, 즉 답변에 전체 내용을 보여 주고 사용자에게 확인을 받는 것이었습니다. 7번 문제에서는 두 설정 모두 요청 안에서 원본 이벤트를 동기적으로 저장하고, Graph API 조회만 백그라운드로 넘겼습니다. 스킬 없음 버전의 9번 문제는 토큰을 URL에 넣어서 `raise_for_status()`가 예외 메시지에 토큰을 노출할 수 있습니다. 이 점은 이미 감점에 반영했습니다(위 표 참고).
- **6라운드**: `debug_token` 변경은 2, 8번 문제에서 효과가 있었습니다. 스킬 있음 버전이 앱 토큰으로 호출하게 되어 90일 권한 승인 확인이 더 이상 Threads 테스터 계정에만 한정되지 않으며, 1–3라운드 2번 문제에서 보였던 제한은 사라졌습니다. 반면 4번 문제의 스킬 있음 답변은 여전히 사용자 자신의 토큰으로 호출하고, 토큰 소유자가 Threads 테스터여야 한다고 설명하며 앱 토큰은 언급하지 않았습니다. 이 점을 다루는 체크 항목은 없습니다. 네 문제 모두 대부분의 체크 항목을 두 설정이 함께 통과했고, 차이를 만든 것은 2번 문제의 8번 항목, 4번 문제의 4번 항목, 7번 문제의 4, 6번 항목, 8번 문제의 7번 항목뿐이었습니다. 채점자는 90일 승인 추적(2번 문제), `debug_token`에 앱 토큰을 쓸 수 있다는 점(4번 문제), 문서대로의 형식으로 온 답글 이벤트가 실제로 데이터베이스에 저장되는지(7번 문제), code 교환이 실패했을 때의 평면 오류 형식을 파싱하는지(8번 문제)를 체크 관점으로 추가하자고 제안했습니다. 스킬 없음 버전의 8번 문제는 `{"error": {...}}` 형식만 파싱하므로, 사용자가 겪은 두 오류가 로그에는 모두 일반 오류로만 표시됩니다. 스킬 있음 버전의 7번 문제는 서명 검증이 계속 실패하면 앱의 기본 secret을 써 보라고 권해, 사용자가 Facebook secret을 쓰게 될 수 있습니다.
- **7라운드**: 스킬 있음은 77개 항목을 모두 통과했고, 이전 라운드보다 점수가 낮아진 문제는 없습니다. 참조 클라이언트를 `scripts/threads_client.py`로 옮긴 뒤에도 스킬 있음의 10개 문제는 모두 SKILL.md를 읽은 다음, 코드를 쓰기 전에 이 파일을 열었습니다. 개발 모드에서는 1, 9번 문제가 `call()`, `check()`, `wait_ready()`, `publish()`를 이식했고(1번 문제는 `threads_publishing_limit`도 먼저 확인), 다른 문제는 `call()`의 오류 처리를 이식하고 게시 흐름과 관계없는 부분은 적절히 생략했습니다. 대리 작업에서는 3번 문제가 3절대로 작업 폴더에서 전체 경로로 클라이언트를 실행해 원래 요청과 두 대안에 각각 `check`를 돌렸고, 사용자에게 넘긴 명령에도 전체 경로를 썼습니다. 반면 10번 문제는 클라이언트를 작업 폴더에 복사해 직접 만든 `post_thread.py`에서 import하고, 스레드를 순서대로 게시하며 오전 8시까지 기다리는 데 썼습니다(클라이언트에는 스레드용 명령이 없습니다). 사용자에게는 수정하지 않은 사본과 이 스크립트를 넘겼습니다. 클라이언트 코드를 다시 입력하거나 임시 파일로 저장한 문제는 없었습니다. 채점자는 체크 항목이 다루지 않는 문제도 몇 가지 지적했습니다. 7번 문제의 스킬 있음 답변은 6라운드와 마찬가지로 서명 검증이 계속 실패하면 앱의 다른 secret을 써 보라고 권했습니다. 10번 문제의 스킬 있음 스크립트는 계정을 출력하지만 8시를 기다리기 시작하기 전에 사용자 확인을 받지 않고, 게시 한도도 확인하지 않습니다. 3번 문제의 스킬 있음이 사용자에게 넘긴 명령은 A안 것뿐이고, 토큰 설정도 넌지시 언급하는 데 그쳤습니다. 채점자의 제안은 다음과 같습니다. 1번 문제는 두 설정 모두 두 라운드 연속 만점이므로 게시 전 로컬 검사(이모지 글자 수 계산 방식, 링크 최대 5개)를 추가하고, 2번 문제에 90일 승인을, 7번 문제에 payload에 `root_post`가 없을 때 게시물을 조회하는지를, 8번 문제에 code 교환 실패 시의 평면 오류 형식 파싱을 추가하며, 9번 문제는 `paging.next`에 의존하지 않는다는 규칙을 체크 항목에 적고, 3, 10번 문제는 두 설정이 모두 통과하는 몇몇 항목을 더 엄격하게 하자는 것입니다.

## 제한 사항

- 문제마다 설정별로 한 번씩만 실행했기 때문에 편차를 추정할 수 없으며, 수치는 경향 정도로만 봐 주세요.
- Claude에서만 평가했고, Agent Skills를 지원하는 다른 도구에서는 실제로 테스트하지 않았습니다.
- 1–4라운드의 API 호출은 모두 채점자가 띄운 모의 서버로 보냈습니다. 5라운드에는 모의 서버가 없었고, 답변 쪽이 로컬 모의 객체나 FastAPI의 TestClient로 자기 코드를 확인했으며 채점자는 코드를 읽고 판정했습니다. 6, 7라운드에도 모의 서버는 없었고, 채점자가 답변 쪽의 테스트를 다시 실행한 뒤 직접 만든 모의 객체로 코드 동작을 실제로 확인했습니다. 어느 라운드에서도 실제 Threads 계정으로 게시하지는 않았습니다.
- 문서에 없는 embed.js 동작과 oEmbed 오류 코드는 2026-10-14에 실제 embed.js를 읽고 oEmbed를 직접 호출해 확인한 뒤 채점자에게 참고 자료로 제공했습니다. Meta가 앞으로 바꿀 수 있습니다.
- 원본 평가 보고서(실행별 전체 답변과 코드 포함)는 repo에 넣지 않았고, 여기에는 채점 데이터만 남겼습니다.
