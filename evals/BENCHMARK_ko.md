# Benchmark 요약

[繁體中文](BENCHMARK.md) | [English](BENCHMARK_en.md) | [日本語](BENCHMARK_ja.md) | **한국어**

threads-api 스킬의 "스킬 있음 vs 스킬 없음" 10라운드 평가 요약입니다. 문제와 체크 항목은 [`evals.json`](evals.json)에, 실행별 항목 판정과 채점자가 첨부한 근거는 [`benchmark.json`](benchmark.json)에 있습니다.

## 평가 설정

| 항목 | 내용 |
|---|---|
| 답변 모델 | `claude-opus-5-5`(스킬 있음, 스킬 없음 두 설정 모두 같은 모델 사용) |
| 채점·분석 모델 | `claude-opus-5-5`, 채점자는 답변에 참여하지 않음 |

라운드 사이마다 채점 의견을 반영해 스킬을 수정했습니다. 1번 문제는 양쪽 모두 만점이라 차이를 가릴 수 없어서 2라운드부터는 2–5번 문제를 사용했고, 3번 문제는 2라운드부터 체크 항목이 하나 늘었습니다. 4라운드에서는 스킬에 11절(게시물 임베드)을 추가한 뒤 6번 문제를 새로 만들어 이 문제만 실행했습니다. 5라운드에서는 7–10번 문제(Webhooks, OAuth 로그인, 코드 리뷰, 스레드 대리 게시)를 새로 만들어 이 네 문제만 실행했습니다. 이 라운드에서는 스킬 없음 설정도 웹에서 공식 문서를 검색할 수 있었고 실제로 Webhooks와 OAuth 페이지를 찾아봤기 때문에, 두 설정의 차이가 이전 라운드보다 작습니다. 6라운드에서는 스킬 1.3 버전으로 2, 4, 7, 8번 문제를 다시 실행해, 아직 평가하지 않은 두 가지 변경을 검증했습니다. 10절의 webhook 중복 제거 규칙과, 8절에서 `debug_token`에 앱 토큰도 쓸 수 있다고 설명한 부분입니다. 이 라운드에서는 두 설정 모두 웹을 쓸 수 없었고 스킬 없음 설정은 모델 자체의 지식만으로 답했으므로, 7, 8번 문제는 5라운드와 그대로 비교하기 어렵습니다. 2번 문제의 스킬 없음과 8번 문제의 두 설정은 도중에 멈춘 뒤, 2026-10-19 11:26(UTC)에 같은 지시로 처음부터 다시 실행했습니다. 7라운드에서는 스킬 1.4 버전으로 10개 문제를 모두 다시 실행해, 14절의 Python 참조 클라이언트를 `scripts/threads_client.py`로 옮긴 뒤에도 퇴보가 없는지 확인했습니다. 스킬은 `threads-api` 폴더 전체(`scripts/` 포함)로 설치했고, 두 설정 모두 웹을 쓸 수 없었습니다. 4번 문제는 이 라운드부터 체크 항목이 7개이며, 새로 추가된 7번 항목은 `debug_token`에 앱 토큰을 쓸 수 있다는 점입니다. 페이지네이션은 6라운드부터의 판정 기준을 따라, 응답에 `paging.next`가 있을 때만 페이지를 넘기는 코드는 불통과로 판정했고, 이 라운드에서는 5, 9번 문제에도 같은 기준을 적용했습니다(2, 3라운드의 5번 문제에서는 이런 코드를 단서를 달아 통과시켰습니다). 이 라운드의 스킬 스냅숏은 14절에 '스킬 파일이 디스크에 없을 때 표준 입력으로 클라이언트를 실행한다'는 설명이 추가되기 약 1분 전에 만든 것이어서, 이 설명은 평가 범위에 들어가지 않습니다.

8라운드에서는 실제 프로젝트 두 개의 경험과 실측에 따라 11절을 고쳐 쓴 뒤 11, 12번 문제(Chrome 확장 프로그램에서 `/embed/`를 직접 임베드한 미리보기, React 컴포넌트 안의 임베드 카드)를 새로 만들어 6번 문제와 함께 실행했고, 두 설정 모두 웹을 쓸 수 없었습니다. 6번 문제의 스킬 없음 답변은 테스트하면서 실수로 브라우저 패널을 써서 실제 embed.js와 임베드 페이지 두 개를 불러와 이 규칙을 어겼지만, 점수는 그대로 계산했습니다. 11번 문제의 3번 항목은 첫 채점 뒤에 결과를 확인하도록(0이 보고되거나 보고가 없을 때 보이지 않는 빈 공간만 남겨서는 안 됨) 고쳐 썼고, 11번 문제는 두 설정의 답변을 새 채점자가 처음부터 다시 채점했습니다. 표에는 다시 채점한 점수를 실었습니다. 이 라운드의 스킬에는 아직 임베드 페이지가 높이를 "한 번만 보고한다"고 적혀 있었는데, 답변이 끝난 뒤 다시 테스트해 보니 이미지가 있는 게시물은 2–4번 보고해서 1.5에서 바로잡았습니다. 9라운드에서는 1.5 버전의 SKILL.md로 같은 세 문제를 다시 실행했고, 세 문제 모두 체크 항목이 하나씩 늘었습니다(각 9개). 두 설정 모두 웹을 쓸 수 없었고, 브라우저 도구로 웹 페이지를 여는 것도 금지했습니다. 이 라운드의 스킬 스냅숏은 11.3절 대체 카드의 원인과 11.1절 oEmbed CORS 설명을 수정하고 버전 번호를 바꾸기 전의 것입니다. 8, 9라운드의 채점자는 2026-10-23에 실측으로 확인한 임베드 동작 목록을 받아, 답변의 주장이 맞는지 판단하는 데 썼습니다. 10라운드에서는 2026-10-24에 보충한 내용(로그인한 사용자에게만 공개된 게시물, 숫자 보고만 인정, 대체 카드의 원인)을 검증하려고 13번 문제(블로그 사이드바의 게시물 3개가 로그인한 사용자에게만 공개됨)를 새로 만들어 실행하고, 퇴보가 없는지 확인하려고 12번 문제를 다시 실행했습니다. 조건은 9라운드와 같습니다. 채점자의 목록에는 그날 실측한 결과도 추가했습니다. 실제로 삭제된 게시물과 로그인한 사용자에게만 공개된 게시물이 oEmbed와 `/embed`에서 각각 어떻게 응답하는지입니다.

## 감점 항목

### 스킬 없음

| 문제 | 감점된 라운드 | 감점 원인 |
|---|---|---|
| 2 | 1, 2, 6, 7라운드 | 페이지네이션에서 `paging.next`만 따라가고 `paging.cursors.after`는 읽지 않았습니다(6라운드에서는 `paging.next`가 있을 때만 읽었습니다). 문서에는 게시물 목록 응답에 `next`가 없다고 명시되어 있어, 문서대로라면 첫 페이지만 가져오게 됩니다. |

"한 번만 보고한다"는 내용의 수정이 효과를 냈습니다. 11번 문제의 스킬 있음 버전은 0보다 큰 보고를 모두 적용해, 채점자가 534, 574, "600"을 차례로 넣자 세 번 모두 적용했고, 세 문제의 스킬 있음 답변 중 한 번만 보고한다고 다시 말한 것은 없었습니다. 새로 추가한 9번 항목은 6번 문제에서는 두 설정 모두 통과했고, 11, 12번 문제에서는 스킬 있음 버전만 통과했습니다. 채점자는 체크 항목이 다루지 않는 오류 하나를 지적했습니다. 12번 문제의 스킬 있음 대체 카드는 "게시물 삭제"를 로드 실패 원인으로 나열했는데, 이 문구는 스킬 11.3절에서 나온 것이지만 삭제된 게시물은 "스레드를 표시할 수 없음"을 보여 주고 로드 성공으로 집계됩니다. 1.5에서 11.3절을 바로잡았고, 수정한 뒤에는 아직 평가하지 않았습니다. 채점자의 그 밖의 제안은 다음과 같습니다. 12번 문제의 7번 항목은 "같은 문서 안에서 embed.js를 다시 삽입하는 데 의존하지 않는지"로 바꾸고, 11번 문제의 9번 항목은 실제 순수 숫자 보고를 처리 함수에 넣어 검증하도록 바꾸며, 11번 문제의 oEmbed 항목에는 확장 프로그램 페이지에서 오류 내용을 읽을 수 있는지도 확인하자는 것입니다(답변 뒤에 실측해 보니 oEmbed의 오류 응답에도 `Access-Control-Allow-Origin: *`가 붙어 있었습니다).

## 제한 사항

- 문제마다 설정별로 한 번씩만 실행했기 때문에 편차를 추정할 수 없으며, 수치는 경향 정도로만 봐 주세요.
- Claude에서만 평가했고, Agent Skills를 지원하는 다른 도구에서는 실제로 테스트하지 않았습니다.
- 1–4라운드의 API 호출은 모두 채점자가 띄운 모의 서버로 보냈습니다. 5라운드에는 모의 서버가 없었고, 답변 쪽이 로컬 모의 객체나 FastAPI의 TestClient로 자기 코드를 확인했으며 채점자는 코드를 읽고 판정했습니다. 6, 7라운드에도 모의 서버는 없었고, 채점자가 답변 쪽의 테스트를 다시 실행한 뒤 직접 만든 모의 객체로 코드 동작을 실제로 확인했습니다. 8–10라운드도 마찬가지이며, 채점자는 순수 숫자 형태의 높이 보고를 답변 쪽의 처리 함수에 직접 넣어 실제로 적용되는지도 확인했습니다. 어느 라운드에서도 실제 Threads 계정으로 게시하지는 않았고, 답변 쪽 코드를 실제 브라우저에서 실제 임베드와 함께 불러온 적도 없습니다.
- 문서에 없는 embed.js 동작과 oEmbed 오류 코드는 2026-10-14에 실제 embed.js를 읽고 oEmbed를 직접 호출해 확인한 뒤 채점자에게 참고 자료로 제공했습니다. 8, 9라운드에서는 2026-10-23에 로컬 테스트 페이지에서 실제 임베드를 불러오고, embed.js를 다시 읽고, oEmbed를 호출해 확인한 목록을 대신 썼고, 10라운드에서는 여기에 2026-10-24에 실제로 삭제된 게시물과 로그인한 사용자에게만 공개된 게시물을 실측한 결과를 더했습니다. 8라운드의 처음 다섯 건의 채점에 쓴 목록에는 아직 "한 번만 보고한다"고 적혀 있었고, 바로잡은 뒤 세 건의 채점에서 영향을 받은 부가 설명을 고쳤으며 항목별 판정은 바뀌지 않았습니다. Meta가 앞으로 이런 동작을 바꿀 수 있습니다.
- 원본 평가 보고서(실행별 전체 답변과 코드 포함)는 repo에 넣지 않았고, 여기에는 채점 데이터만 남겼습니다.
